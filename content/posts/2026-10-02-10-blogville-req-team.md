오늘의 팀 목표는 **요구사항 명세서를 세세하게** 쓰는 것이었다.

## 1. 양식부터 만들었다

한 줄짜리 요구사항("아이디로 회원가입할 수 있다")을 아래 칸으로 나눴다.

| 칸 | 내용 |
|---|---|
| 우선 / 상태 / 담당 | MoSCoW · ✅🚧⬜❌ · 담당자 |
| 사용자, 선행 조건, 관련 | 누가, 어떤 상태에서, 어느 화면·테이블 |
| 기본 흐름 | 문제가 없을 때 순서 |
| 예외 흐름 | 틀렸을 때 **보여줄 문구 그대로** |
| 입력 규칙 | 길이, 허용 문자 |
| 표시 규칙 | 개수, 정렬, 자르는 길이 (피드백 반영) |
| 구현 방식 | 화면·처리·데이터·무결성·검증·갱신 (피드백 반영) |
| **수용 기준** | 이걸 만족하면 완성. 테스트 시나리오로 그대로 쓴다 |
| 열린 질문 | 모르는 건 지어내지 말고 회의에서 정한다 |

**수용 기준**이 특히 중요하다고 느꼈다. "완성"의 기준이 팀원마다 다르면 나중에 꼭 다툼이 생긴다.

쓰다 보니 "회원가입·로그인"이 한 요구사항에 붙어 있어서 **AUTH-07(가입)과 AUTH-09(로그인)로 나눴다.** 요구사항 ID는 한 번 정하면 바꾸지 않는다는 규칙도 정했다. 다른 문서와 코드가 ID로 서로를 가리키기 때문이다.

## 2. 영역을 나눴다

| 담당 | 영역 |
|---|---|
| 나 | 회원·인증, 비기능 |
| 팀원 1 | 블로그, 글, 교류 |
| 팀원 2 | 캐릭터·성장, 상점·꾸미기, 광장 |

각자 GitHub Issue를 받고, 자기 브랜치에서 써서 PR로 올린다.

## 3. 팀원 PR 리뷰

팀원 한 명이 482줄짜리 PR을 올렸다. 적힌 내용을 **실제 코드와 하나씩 대조**했다.

- 오류 문구, 버튼 상태 순서, 광장 크기·이동 속도·상호작용 거리 같은 숫자가 **전부 코드와 일치**했다.
- 내가 놓친 문제도 찾아 줬다: 모바일 헤더에서 레벨이 숨겨짐, 고르지 않은 기본 캐릭터 2종은 영영 얻을 수 없음
- 리뷰하면서 버그를 하나 더 찾았다: 출석 화면의 "최근 연속 N일"이 **이번 달 기록만** 봐서, 9/30에 출석하고 10/1에 열면 연속 중인데도 0일로 보인다.
- 체크된 수용 기준 중 E2E로 확인한 것과 코드만 본 것을 구분하자고 제안했다.

## 4. 피드백 반영: 구현된 것도 전부 적기

[두 번째 피드백](#/post/feedback-impl-details)을 받고 모든 영역에 **표시 규칙**과 **구현 방식**을 채웠다. 값은 기억이 아니라 코드에서 직접 뽑았다.

| 영역 | 예시 |
|---|---|
| 글 목록 | 한 페이지 8개, 요약 160자·2줄, 페이지 번호 앞뒤 2개 |
| 태그 | 글 하나에 최대 10개, 각 20자, 소문자로 저장, 인기 태그 30개 |
| 광장 | 화면 높이 68%, 이웃집 최대 8채, 상호작용 거리 90px |
| 관리자 | 최근 가입 20명, 최근 30일 글 30개 |

상세 명세가 있는 요구사항이 27개에서 **49개**가 됐다.

## 5. 적으면서 발견한 것

코드를 문장으로 옮기다 보니 "이게 맞나?" 싶은 부분이 보였다. 바로 고치지 않고 **열린 질문**으로 남겨 팀에서 정하기로 했다.

1. 블로그 주인이 볼 때 "전체 글 (N)"은 공개 글만 세는데 목록에는 비공개 글도 나온다
2. 조회수가 같은 사람이 새로고침해도 계속 오른다
3. 태그가 10개·20자를 넘으면 안내 없이 조용히 빠진다
4. 다른 블로그의 카테고리 번호를 주소에 넣으면 "전체 글 0개"가 나온다

> 명세서를 쓰는 건 단순히 문서 작업이 아니라, **만든 것을 다시 검토하는 과정**이었다.
